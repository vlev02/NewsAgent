### 🔥 今日必看

- **vLLM RFC #57103 "Programmable KV Cache: Composable Policies for Agentic Serving"**
  （GitHub, vllm-project/vllm#57103）— vLLM 提出 provider-neutral 的"可编程 KV Cache"抽象：router
  侧提供 session 生命周期/放置意图，engine 侧多个可组合 policy 针对共享内存压力快照提出
  retention/movement/quota 动作，双方之间建立统一的资源审批/完成协议；动机数据来自 vLLM AgentX
  真实线上流量（session 中位数 43 轮、输入中位数 142K token、prefix-cache 命中率 >96%、44% 的
  session 带有 subagent）。三个独立检索路径（tier_0/tier_1/tier_2）均命中此 RFC，是本轮信号强度
  最高的发现。
  **对 StructKV 的意义**：直接落在 P3（协议与 SGLang 执行）——这是 vLLM 第一方在做"Agent Runtime
  ↔ Serving 接口传递结构/会话语义"的真实工程实践，回答了接口边界调研中"StructKV 插入点在哪"的
  问题：插入点应该是 router→engine 之间的 policy 协商层，而非 tokenizer/chat-template 层。但它
  只定义了 policy 组合的协议骨架，既未给出"结构信号（episode 边界/工具调用状态/依赖图）→具体剪枝
  决策"的算法（P2 的空白），也未声明其 retention/movement 操作是否满足 prune+reindex 的原地安全性
  （P1 ReClaim 的空白）——这两处正是 StructKV 需要补上的差异化贡献。

### ⚠️ 竞品预警

- **vLLM RFC #57103**（同上，详情见"今日必看"）— **重叠点**：用 session/结构化意图驱动 KV 层
  retention/movement 决策，且明确以 engine-side policy 而非 orchestrator 重发 prompt 的方式执行，
  与 StructKV"结构信号→KV 指令→原地执行"的主张同构。**StructKV 差异还剩什么**：#57103 只是 policy
  组合的协议/资源审批框架，不含具体决策算法（P2：如何从 episode 边界/工具调用状态/依赖图算出该
  保留/剪枝哪些 KV），也未证明其执行满足 prune+reindex 的位置安全性（P1 ReClaim）；StructKV 的
  空间是把这两块的具体算法和安全性证明做扎实，并可以考虑直接把 StructKV 原型接到这个正在成形的
  协议骨架上做验证。

- **TokenPilot（核心竞品，arXiv 2606.17016）版本更新 v1→v2**（2026-08-28 修订，此前 digest 未
  跟踪到该版本更新）— **重叠点**：TokenPilot 本身就是已跟踪的核心竞品，采用 Ingestion-Aware
  Compaction（全局前缀稳定）+ Lifecycle-Aware Eviction（残余效用驱逐）双粒度机制，是"结构化生命
  周期信号→KV 驱逐决策"思路的直接实例。**StructKV 差异还剩什么**：受 egress 限制未能直接核实 v2
  与 v1 的具体 diff（检索到的摘要/主张与已知 v1 一致：隔离/连续模式下最高降本 87%），已知 v1 机制
  仍是效用打分式的驱逐，而非显式的 episode/tool-call 状态机驱动的 prune+splice+reindex；StructKV
  在决策算法的可解释性（P2，依赖显式状态标记而非隐式效用打分）与 reindex 安全性证明（P1）上仍有
  差异化空间，但需要找时间通读 v2 全文确认其是否已经补上这块，留作后续动作项。

### 🔗 Agent ↔ Serving 接口

- **vLLM RFC #48501 "Session-centric KV-cache orchestration over typed session identity"**
  （2026-07-13 开，vllm-project/vllm#48501）— 在 engine 之上建一层控制面，以"typed session
  identity"作为一等原语，retention/offload/move 都设计成 intent-free primitive，并提出
  "indexer"作为集群级语义内存映射。**对 StructKV 的意义**：直接回答接口边界调研中"Episode 表达"
  的问题——目前工程实践里最小语义主键还停留在 session 级，尚未细化到 episode/tool-call 子粒度，
  这正是 P3 执行层需要补上的粒度落差。
- **SGLang RFC #24656 "[RFC] Agent-Aware KV Cache Phase 1 for Agentic Workloads"**（2026-05-08
  开）— 打通了一条从 API 层→runtime request→radix cache node 的最小 metadata 通路，新增可选
  `agent_hints` 字段喂给实验性 `agent_aware` radix 驱逐策略。**对 StructKV 的意义**：直接回答
  "ID 在哪层丢失"——目前只做到字段级 hint 透传，尚未把 episode 边界/工具调用状态结构化编码进
  block 元数据，这是 P3 协议设计需要补的细节。
- **SGLang RFC #27574 "[Agentic Inference] Programmatic KV Cache for Agentic Workloads"**
  （2026-06-08 开）— router 发起 hint，engine 保留裁决权（可裁剪/推迟/拒绝）。**对 StructKV 的
  意义**：提供了 P3 协议设计的一个参照点（engine 保留最终裁决权），同样未定义结构信号的具体编码
  格式，是待填的空白。
- **vLLM RFC #37003 "Context-Aware KV-Cache Retention API (Prioritized Evictions)"**（2026-03-13
  开，已有 PR #38514 落地实现）— priority+TTL 的 retention 指令，orchestrator=policy /
  engine=执行的分工。**对 StructKV 的意义**：是 P3 执行侧目前唯一已经合并落地的原语，可以作为
  StructKV 原型的宿主接口，验证 P1 的 prune+reindex 能否直接塞进已有的 retention API，而不用等
  vLLM 把完整的 Programmable KV Cache（#57103）做完。
- **vLLM PR #51381 "[Core][KV Events] Echo session_id on GPU BlockStored events"** — 在 GPU
  BlockStored 事件里回传 `session_id`，是"跨层传递 block 元数据"目前唯一已落地的具体最小实例。
  **对 StructKV 的意义**：量化了"ID 在哪层丢失"这一问题的现状基线——当前 serving 层 block 元数据
  通道只携带 session_id 这种粗粒度标识，还不携带 episode/tool-call 级别信息。
- **vLLM Blog "vLLM x AgentX: Optimizing for Real-World Agentic Serving"**（2026-09-08）—
  上述多条 RFC 的动机数据来源（session 中位 43 轮、输入中位 142K token、prefix-cache 命中率
  >96%、44% session 带 subagent）。**对 StructKV 的意义**：是 P2 E1（有效性实验）可以直接引用的
  真实 workload 分布参数，避免自造不真实的合成 workload。

### 📊 Workload 与证据

- **gauravapiscean/agentic-kv-cache**（GitHub 社区复现研究）— 在 6.8 万请求 / 393 个 Claude Code
  会话的真实 trace 上复现常见 agentic KV-cache policy 论文声称的收益，发现 LRU 比论文里描述的更
  难打败。**对 StructKV 的意义**：是 P2 E2（StructKV 决策与简单 baseline 的分歧率）实验最现实的
  对照基线来源——如果连精心设计的 policy 都很难稳定超过 LRU，StructKV 在 E2 里必须讲清楚自己的
  分歧判断具体在哪些 case 下才真正带来收益，而不能笼统声称"优于 LRU"。
- **Yandex Research Blog "The KV cache as an agent runtime"**（2026-09-05）— 提出把 KV cache
  当作共享状态 runtime，让模型在新信息流入时并发观察/推理/行动而无需重启；SGLang 实现+自定义
  kernel 在做，正式论文"即将发布"，以 Doom 游戏为 testbed。**对 StructKV 的意义**：是 P3 方向上
  一个尚未发表但需要盯住的潜在方案——其"不重启"的核心主张与 StructKV 高度接近，目前仅有博客、
  机制细节未知，先记录为观察点，论文放出后第一时间判断是否构成竞品。

### 📦 Baseline 动态

- **StepKV: Step-Aware KV Cache Compression for LLM Agents**（arXiv 2609.22158，CUHK/华为）—
  把 agent 推理轨迹拆成信息获取/假设/推导/决策等离散推理步，在 token 级 KV 选择之上叠加 step 级
  重要性打分；首次把"推理步"这一结构单元用作 agent 场景 KV 压缩的打分依据，满足 tier_3 进入条件
  (b)（agent 场景首次评测），但机制仍是重要性打分式压缩，而非显式的 episode/工具调用状态驱动的
  prune+splice，故只进本区，不进"今日必看"。
