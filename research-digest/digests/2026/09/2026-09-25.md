### 🔥 今日必看

- **RFC: Agent-Aware KV Cache Affinity Scheduling and Lifecycle Management**（同一作者 daisyEliot，
  2026-09-25 当天同步开在三个项目：vllm-project/aibrix#2814、llm-d/llm-d#2584、
  volcano-sh/kthena#1828，均已通过 WebFetch 核实真实存在）— 指出 agent workload 已占生产流量
  40–60%，但现有 KV 缓存栈缺 5 类语义感知能力：路由不感知"同一 agent 程序"身份（导致重复
  prefill）、驱逐不区分 context 类型（system prompt 与临时推理状态同权重）、缓存生命周期与
  agent 工具调用空闲期脱钩（idle 时被当冷数据驱逐，resume 时被迫重新 prefill）、KV 事件协议
  不携带 agent 语义元数据、缺少面向可预测多轮模式的主动/投机 prefill。提议引入标准化
  `agent_hints`（`program_id` / `priority` / `context_type` / `session_ttl_hint` 等字段）、
  program-affinity 路由、按 context 类型加权的驱逐分数、`open`/`heartbeat`/`close` 会话生命周期
  信号、以及空闲算力窗口的投机 prefill；全部设计为向后兼容的可选扩展。
  **对 StructKV 的意义**：直接命中 P3（协议与 SGLang/vLLM 执行）与接口边界调研的核心问题——
  "agent 结构语义该用什么字段、在哪一层跨层传递给 KV 策略"。`agent_hints.context_type` 与
  `session_ttl_hint` 是这个问题的又一具体候选答案，且与昨日收录的 vLLM #58537
  （`vllm_xargs.kv_edit`，显式声明死区）、agentic-api #364（typed 执行事件送入 llm-d 缓存策略）、
  以及已跟踪的 SGLang RFC 链（#24656→#27574→已合并 PR #37482）在同一周内构成第 4/5/6 个平行提案
  ——不同项目、不同字段命名，但都在收敛到"结构化 agent 元数据需要成为 KV 事件协议的一等字段"
  这一结论，为 P3 协议设计提供了跨项目的收敛证据。

### ⚠️ 竞品预警

- **aibrix#2814 / llm-d#2584 / kthena#1828（同一 RFC 三项目同步提案）** — 重叠点：`agent_hints`
  携带的 `program_id`（对应 StructKV 的依赖/程序身份）与 `context_type`（对应结构化语义标签）
  直接驱动驱逐加权与会话固定，是"结构信号 → KV 层保留/驱逐决策"这一 StructKV 核心主张的又一
  字面实现，且首次同时覆盖 3 个不同的 serving/调度项目（AIBrix、llm-d、Kthena），扩散速度快于
  此前任何单一竞品。StructKV 差异还剩什么：`agent_hints` 目前只是"打标签"——`program_id` /
  `context_type` 仍由上层 agent/orchestrator 自行赋值，RFC 本身不提供从 episode 类型、工具调用
  生命周期、依赖图等结构信号自动推导这些标签值的决策算法（P2 仍是空白）；驱逐加权和会话固定也
  停留在打分/TTL 语义，未见到显式的 prune+splice+reindex 原地编辑原语（P1/P3 执行侧仍有区分空
  间）。三项目均为今日刚开的 RFC（0 条讨论回复），距落地尚早，值得持续追踪其接口是否收敛，以及
  与已跟踪的 vLLM #58537 / agentic-api #364 / SGLang 链之间是否会合并成统一标准。
