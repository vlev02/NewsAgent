### 🔥 今日必看

- **[RFC]: KV Context Editing — Relaxed Prefix Alignment for KV Allocation and Reuse**（vLLM
  GitHub Issue #58537，作者 yxkyong，2026-09-24 当天提出）— 提出 `vllm_xargs.kv_edit`：agent 在
  请求级别按 message index / 字符偏移声明历史中的某些片段"语义已死"（如已被消费的工具结果、被
  取代的中间推理），引擎保证明文不变、token 位置不变、完全覆盖的死区不占新显存、下游缓存块仍可
  复用；跨越编辑边界的块只付出少量 attention mask 开销。核心卖点是"做到明文删除做不到的事——
  消除语义死重而不需要后缀重算"，并显式维护 hash 链完整性以保持 prefix cache 有效。
  **对 StructKV 的意义**：几乎是 P3（协议与 SGLang/vLLM 执行）在 vLLM 侧的字面落地——直接回答了
  "StructKV 插入点"这个接口调研问题：请求级 `kv_edit` 字段就是一个现成的候选插入点。但它的"哪些
  range 语义已死"仍由上层 agent/orchestrator 自行判断并显式声明，本身不提供从 episode 类型 / 工具
  调用生命周期 / 依赖图等结构信号自动推导决策的算法（P2 空白仍在）；StructKV 的差异化空间在于把
  "怎么判断该编辑哪里"这一步做实，而不是"编辑接口长什么样"。
- **Connect agentic execution signals to session-centric KV policy**（GitHub Issue #364，
  vllm-project/agentic-api，作者 franciscojavierarceo，2026-09-23）— 提议把 Agentic API 已解析
  的 lineage 与执行生命周期（工具执行、未来推理轮次、上下文变化）暴露给 llm-d，让缓存策略能感知
  这些事件；定义了六条验收标准，包括推导租户级会话身份、为多种执行事件发出类型化信号、验证这些
  信号如何影响保留策略；依赖 #360/#361，并与 #363 集成。**对 StructKV 的意义**：这是"message/
  tool-call 边界元数据如何跨层传递"这条接口调研线索的最新数据点——把"typed 执行事件"作为一等
  信号从 Agentic API 层显式送到 llm-d/vLLM 缓存策略层，与已跟踪的 vLLM #37003（优先级/TTL 保留
  API）、SGLang RFC 链（#24656→#27574→已合并的 PR #37482）构成同一问题在不同项目上的并行实例；
  P3 协议设计时值得比较三者对"信号类型化粒度"的不同取舍。
- **Aborted but Not Forgotten: KV-Cache Retention Breaks Rollback Consistency in Language
  Agents**（arXiv 2608.15939，8/16，Guijia Zhang / Harry Yang，香港科技大学）— 有状态 agent 默认
  "清空 transcript 就等于回滚"，但当 serving session 跨越逻辑 abort 保留 KV cache 时这个假设失效；
  论文将缺失的保证形式化为 rollback consistency：一次被认为完整的 abort 必须恢复模型实际 attend
  到的状态，而不只是可见的 transcript。用同 token / 不同 cache 的审计方法（决策步 token 固定，只
  改变缓存前缀是否陈旧或从已提交状态重建）在 7 个开源模型家族（3.8B–36B）上测试，发现仅靠保留的
  KV 就能在 63 个被审计单元中的 25 个翻转一个受保护效应，构成跨层的安全问题——应用复用 session
  handle 或缓存的 past_key_values 以求低延迟时，可能无意中通过模型保留的 KV cache 泄露本应被
  丢弃的内容。9/17 曾因超出 7 天窗口留待确认是否已收录，本轮核实 papers.jsonl 全量历史中从未
  收录，予以补录。
  **对 StructKV 的意义**：直接命中 P1（ReClaim，prune+reindex 原地安全性）——这篇不是提出剪枝
  机制的竞品，而是从反面给出了目前收录到的最锋利的安全性证据：如果 abort/retry 这类 agent 结构
  标记不能在 KV 层触发真实的状态改变（哪怕只是逻辑上"应该已删除"），就会产生可审计出的正确性/
  安全漏洞。这给 P1 的 reindex 安全性证明划出了一条具体、可复现的正确性判据（rollback
  consistency），后续 ReClaim 的证明应该显式覆盖这个场景。
- **From Research Paper to Real Workload: KV-Cache Editing with the LMCache SDK**（LMCache
  官方 blog，2026-09-07）— 描述一个生产级 SDK，把 KV cache 的检索与编辑放在 CPU 上执行、脱离
  主 GPU 推理路径，从而把编辑工作负载与推理调度/算力解耦；引入"stream"抽象表示单个请求的
  cache-编辑生命周期，多个 stream 可组合成 `LMCacheBatchedStream` 并发批量执行，使研究者不需要
  为算法评测单独实现一套批处理逻辑。明确定位为把已发表的 KV 编辑研究（token dropping、cache
  training 等）落地为可部署的 serving 组件。
  **对 StructKV 的意义**：是 P3 论题"原地编辑执行不走文本重发"的生产系统实证——一个真实、可用的
  KV 编辑执行层已经存在于 LMCache 这一主流开源项目中。**竞品重叠**：核心执行原语（CPU 侧原地
  编辑、批量并发、与推理路径解耦）与 StructKV 的执行侧主张直接重合；StructKV 差异还剩什么——
  LMCache SDK 提供的是通用编辑执行基础设施，"编辑什么/何时编辑"仍由调用方决定，不内置从 agent
  结构信号推导决策的算法（P2），这正是 StructKV 需要补上的部分。

### ⚠️ 竞品预警

- **vLLM #58537 (KV Context Editing)** — 重叠点：agent 声明死区 → 引擎原地编辑、不重新 prefill、
  保留 prefix cache 有效性，是 StructKV 执行侧主张的字面实现。StructKV 差异还剩什么：#58537 的
  死区判定完全外包给上层显式声明，不提供从 episode/工具调用/依赖图等结构信号自动生成决策的算法
  ——这正是 P2 要补的部分；此外它是尚未合并的 RFC 阶段提案，值得持续跟踪其是否落地及最终接口
  形态是否变化。
- **agentic-api #364 (session-centric KV policy signals)** — 重叠点：把 agent 执行生命周期的
  类型化信号显式送入 serving 层缓存策略，与 P3 协议设计的核心问题（信号如何跨层传递）直接对应。
  StructKV 差异还剩什么：目前信号粒度仍是会话/租户级身份 + 事件类型，未见到细粒度到 episode
  边界或依赖图层面的规范；且该 issue 本身依赖另外两个未完成的 issue（#360/#361），距离可用还有
  距离，StructKV 若能先给出细粒度信号 schema 的具体设计，仍有先发空间。
- **LMCache SDK: KV-Cache Editing blog** — 重叠点：CPU 侧原地 KV 编辑、脱离推理路径、面向真实
  workload 的执行系统，直接对应 StructKV 执行侧（P3）主张。StructKV 差异还剩什么：SDK 只解决
  "怎么编辑"，不解决"编辑什么"——决策算法（P2）仍完全开放，且该 SDK 目前面向研究者把已有算法
  接入 workload，尚未看到与 agent 结构信号（工具调用状态、依赖图等）绑定的决策层。

### 📊 Workload 与证据

- **The KV Cache Working Set: Online Capacity Planning for LLM Inference Systems**（arXiv
  2609.27746，9/23，Luchang Li / Shuaishuai Wang / Zhao Ruan / Dongfang Li / Bozhao Gong）—
  面向 agentic workload（工具调用、不断增长的会话历史）的 prefix cache 容量规划问题：为保留全部
  历史 KV 状态而配置容量代价过高，容量不足又会显著拖累命中率；提出 KVSET，用 Mattson stack
  算法在线估计不同缓存容量下的命中率曲线，指导容量规划。
  **对 StructKV 的意义**：是"为什么要做原地剪枝而不是简单地多买显存"这条经济性论证的补充证据——
  量化了 agentic workload 下"全量保留"在容量上的不可行性，为 P1/P2 的动机部分提供了新的、更
  贴近生产容量规划视角的数据点，但本身不涉及结构信号驱动的决策算法。
- **TrajectoryDB: A New Database for Agent Trajectories [Vision]**（arXiv 2609.07782，9/7，
  Yunjia Zheng / Juncheng Yang，哈佛大学）— Vision 论文，主张 agent 执行轨迹应作为独立数据类型
  管理：轨迹同时具有层级执行结构、大量需要语义推理的文本、以及事件/中间状态/衍生产物之间丰富的
  依赖与 lineage 关系；今天数据分散在文件、数据库与可观测性系统之间，缺乏围绕这种结构与访问
  模式设计的持久化数据管理系统。设想 TrajectoryDB 联合设计 ingestion/存储/查询三层来管理这类
  轨迹数据。
  **对 StructKV 的意义**：是接口边界调研中"Episode 表达应该放在哪一层"问题的又一数据点——这次
  的答案落在"轨迹原生的独立数据管理系统"这一层，而不是 runtime 内部或 serving engine 内部；
  它对"结构信号"（层级执行结构、依赖/lineage）的建模方式，可以作为 StructKV 设计 episode/
  依赖图 schema 时的一个参考坐标，但目前仍是 vision 阶段，无落地系统可评估。
