### 🔥 今日必看

- **AKV: Cache Engineering for Agents（GitHub thu-nics/AKV，对应 arXiv 2610.28577，清华 NICS）**— 代码已公开：`akv.agent` 决定丢弃哪些 message 的 KV、何时对保留 token 做 reposition；`akv.system` 基于 SGLang，通过 OpenAI-compatible Chat Completions 请求里新增的 `drop_message` / `reposition` 字段执行，先 drop 再 reposition，保留部分复用 KV、不重新 prefill。CachePolicy 拆成 trigger / selector / reposition 三部分，另有 `DropContextTool`，可让 agent 自己调用 `drop_context` 排期丢弃不再需要的 tool result。<https://github.com/thu-nics/AKV>
  - 对 StructKV 的意义：P3（协议与 SGLang 执行）+ 接口边界调研：这是目前最接近“agent 语义 → message 级 KV 删除 + position 压缩 → SGLang 原地执行”的公开实现，且把 message 粒度的指令塞进了标准 chat 请求。可直接回答“ID 在哪层丢失”和“StructKV 插入点”：message 边界在请求层就被保留。同时是 P1 的外部参照：reposition 的触发时机与正确性验证口径。

### ⚠️ 竞品预警

- **AKV / Cache Engineering for Agents（github-thu-nics-akv ↔ 2610.28577）**— 重叠点：agent 侧信号（tool-result 轮次、agent 自主 drop）驱动 KV 层按 message 删除，并做 position 压缩，在 SGLang 上原地执行、不重新 prefill，即 StructKV 的核心管线。这一条由“论文摘要级预警”升级为“有可运行代码的竞品”。
  - StructKV 还剩的差异（依据 README，需读全文确认）：AKV 的选择器看起来按 turn / message / tool result 粒度，由人工规则或 agent 自选；尚未见 episode 类型、依赖图、失败 / 覆盖 / 重试标记作为一等信号，也未见对 prune+reindex 安全性（P1 ReClaim）的专门论证，也没有 E2 式的结构信号 vs 注意力信号分歧率分析。P2 的 E1 需要把 AKV 的 rolling-drop 策略作为必选对照，P3 需对比其 `drop_message` / `reposition` 协议与我们的指令集。

### 🔗 Agent ↔ Serving 接口

- **AKV 的请求级接口**（见上，同一条目）：`drop_message` 指定被丢弃 message 及生效时机，`reposition` 指定何时压缩位置。适合与 SGLang RFC #45189（KvHintsEnvelope）对照：前者已有内容级 drop + reposition，后者仍只有 priority / 迁移类动作。
  - 对 StructKV 的意义：接口边界调研（StructKV 插入点）——两者合起来说明 SGLang 侧缺口正在被不同团队各自补上，P3 协议需要尽快明确与二者的关系。

### 📊 Workload 与证据

- **Serving Agentic Workloads at Scale with vLLM x Mooncake**（vLLM 官方 blog，2026-05-06）— 在 agentic traces 上加入分布式 KV 池后，缓存命中率从 1.7% 升到 92.2%，并给出吞吐与延迟收益；仅依据搜索摘要，厂商自测。<https://vllm.ai/blog/2026-05-06-mooncake-store>
  - 对 StructKV 的意义：P2 E1 动机数据——整块 / 前缀级缓存在 agent 轨迹上的命中上限，以及“只靠扩容也能把 re-prefill 压下去”的反方论点，需要在 E1 中说明结构驱动剪枝相对扩容的收益。
