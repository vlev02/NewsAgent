### 🔗 Agent ↔ Serving 接口

以下两条是首次收录的既有 GitHub RFC（并非过去 48 小时新发），补入是因为它们直接回答接口边界问题。

- **[RFC] Context-Aware KV-Cache Retention API（vLLM issue #37003，2026-03-13 开，仍 open）**— 提出 token 区间保留指令 `RetentionDirective{start, end, priority 0-100, duration}`，经 `extra_body` 随请求传入，可选 `retention_scope`（通常是 session ID）；无指令的 block 仍走 LRU。设计原则是"orchestrator 定策略，vLLM 执行"。动机数据：工具调用暂停期间并发 agent 的 LRU 驱逐造成 40–60% cache miss。
  - 对 StructKV 的意义：**P3 / 接口边界（Episode 表达、StructKV 插入点）**——这是"token span 级指令跨层传递"的另一份先例（vLLM #58537 是 message 空间的 `kv_edit`，本条是 token 区间 + 优先级）。它只表达保留优先级，没有删除 / 拼接 / reindex 语义，也没有 episode 或依赖结构；StructKV 协议可定位为"在同一 span 通路上增加编辑类指令，并由结构信号生成 priority/delete 决策"。
- **[RFC] Agent-Aware KV Cache Phase 1（SGLang issue #24656，2026-05-08 开，stmatengss，仍 open）**— 在 OpenAI 兼容请求里加可选 `agent_hints`：`workflow_id / agent_id / step_id / step_index`、父子 step 关系、`tool_name`、`expected_tool_duration_ms`、`cache_ttl_ms`、`shared_prefix_hash`、`reuse_hint`；调度器侧追踪 workflow DAG，radix cache 节点打元数据标注，新增 `agent_aware` 驱逐策略原型。Phase 1 明确不做 `shared_prefix_hash` 驱动的复用与 HiCache 集成。
  - 对 StructKV 的意义：**P3 / 接口边界（ID 在哪层丢失、StructKV 插入点）**——step / tool 级 ID 与 DAG 在请求层进入 serving，并落到 radix 节点元数据，说明"结构 ID 跨到引擎内部"在 SGLang 里有落点；但粒度是 step 而非 episode，且只驱动驱逐优先级与 TTL，不触发 prune+reindex。与 SGLang #27574（Programmatic KV Cache，已跟踪）合看，SGLang 侧已有两条 hint 类 RFC，都没有编辑原语。
